# حافظ‌تیک — HafezTick

برنامه‌ریزی روزانه و هفتگی، **ثبت ساعت مطالعه**، و دیدن اینکه در گذر زمان واقعاً چقدر وقت گذاشته‌ای.

حافظ‌تیک یک To-Do ساده نیست، و «کار انجام‌شده» را هم نمی‌شمارد: برای هر فعالیت **زمانی که صرفش کرده‌ای** را وارد می‌کنی، و پیشرفت روز از روی مجموع همان ساعت‌ها نسبت به **هدف ساعتی همان روز** حساب می‌شود. هر روز که می‌آید، برنامه‌ی آن روز **ثبت و قفل** می‌شود، و آمار از روی همان سابقه‌ی واقعی ساخته می‌شود — نه از روی برنامه‌ی امروزِ تو.

تایمری در کار نیست: زمان را خودت اندازه می‌گیری و وارد می‌کنی؛ سایت دفترِ ثبت و تحلیل است، نه کرنومتر.

---

## چه چیزی دارد

- **امروز** — حلقه‌ی ساعت مطالعه‌ی روز، ثبت زمان برای هر فعالیت، بازگردانی سریع، کارهای عقب‌افتاده
- **هفته** — تخته‌ی هفت‌روزه با گلِ اختصاصی هر روز، ساعت مطالعه‌ی هفته تا امروز، سبد کارهای بی‌تاریخ
- **روتین‌ها** — تکرار روزانه / روزهای معیّن / «چند بار در هفته»، با ساعت‌های ثبت‌شده در ۳۰ روز اخیر
- **آمار** — زنجیره، نقشه‌ی پایبندی (heatmap) بر اساس درصد هدف ساعتی، نمودار روند، مقایسه‌ی میانگین ساعت روزانه، ساعت هر دسته و هر روز هفته
- **تنظیمات** — هدف ساعتی روزانه، **هدف مستقل برای هر روز هفته**، قانون «روز موفق»، روزهای استراحت، ۹ رنگ دسته، پشتیبان‌گیری و بازیابی (تم از نوار کناری عوض می‌شود)

### تصمیم‌های محصولی که مهم‌اند

| تصمیم | چرا |
| --- | --- |
| واحد پیشرفت **دقیقه** است، نه تعداد تیک | چهار کار کوچک و یک کار پنج‌ساعته نباید یک اندازه ارزش داشته باشند |
| هر روز هفته **هدف ساعتی خودش** را دارد | شنبه‌ی شش‌ساعته و پنج‌شنبه‌ی دوساعته باید هر دو بتوانند «روز موفق» باشند |
| «روز موفق» یعنی رسیدن به درصدی از هدف **همان روز** | مقایسه‌ی منصفانه بین روزهایی که توقع یکسانی از تو ندارند |
| **تایمر داخلی وجود ندارد** | دقتِ ثبت نباید به باز ماندن یک تب مرورگر گره بخورد؛ سایت دفتر است، نه کرنومتر |
| برنامه‌ی هر روز هنگام رسیدن آن روز **ثبت می‌شود** | ویرایش یا حذف یک روتین، تاریخِ گذشته را بازنویسی نمی‌کند |
| «امروز لازم نبود» کار را کنار می‌گذارد و زمانش را هم صفر می‌کند | کنار گذاشتن آگاهانه‌ی یک کار نباید شکست حساب شود |
| ساعت‌های روتین «چند بار در هفته» به روز اضافه می‌شود، ولی سهمش هفتگی می‌ماند | وقتی که گذاشته‌ای وقت است؛ اما تعهدش هفتگی است، نه روزانه |
| روزِ **بدون هدف** (هدف صفر) و روزهای استراحت، زنجیره را نمی‌شکنند | زنجیره باید انگیزه بدهد، نه اضطراب |
| امروزِ ناتمام هرگز زنجیره را نمی‌شکند | روز هنوز تمام نشده است |
| بیش از هدف رفتن **پنهان نمی‌شود** (درصد از ۱۰۰ رد می‌شود) | روزی که هشت ساعت خوانده‌ای با روزی که شش ساعت خوانده‌ای یکی نیست |

## معماری

```
src/
  app/                 صفحه‌ها (App Router)
  components/
    ui/                اجزای پایه‌ی رابط کاربری
    layout/            پوسته، ناوبری، تم
    tasks/             ردیف کار، ثبت زمان، دیالوگ‌ها
    today/ week/       اجزای مخصوص هر صفحه
    charts/            نمودارهای SVG اختصاصی
  lib/
    date/              تقویم جلالی و ابزار روز (خالص، تست‌شده)
    domain/            مدل، زمان‌بندی، هدف ساعتی، امتیازدهی، آمار (خالص، تست‌شده)
    utils/             قالب‌بندی مدت زمان و مقیاس رنگی مرحله‌ای
    storage/           Repository و آداپتور محلی
    store/             AppStore + اتصال React
```

**قاعده‌ی اصلی:** `lib/` هیچ چیزی از React یا DOM نمی‌داند. همه‌ی منطق — تبدیل تاریخ، ساخت برنامه‌ی روز، امتیاز، زنجیره، آمار — تابع خالص است و تست دارد. کامپوننت‌ها فقط نمایش می‌دهند و اکشن صدا می‌زنند.

### مدل داده

سه موجودیت اصلی، و یک واحد که همه‌چیز بر آن بنا شده است:

- `Routine` — کار تکرارشونده (قاعده‌ی تکرار)
- `Task` — کار یک‌بارمصرف (یک روز، یا سبد کارها)
- `Entry` — **واحدی که زمان روی آن ثبت می‌شود و آمار از آن ساخته می‌شود**

`Entry.minutes` تنها ورودیِ همه‌ی عددهای پیشرفت است. زمان به **دقیقه** ذخیره می‌شود چون عدد صحیح است؛ ساعت اعشاری بعد از چند جمع، دقتش را از دست می‌دهد. تبدیل به «۲ ساعت و ۳۰ دقیقه» فقط در لبه‌ی رابط کاربری اتفاق می‌افتد.

`Entry` عکسِ لحظه‌ای از برنامه است: وقتی روزی فرا می‌رسد ساخته می‌شود و بعد از آن دست‌نخورده می‌ماند. روزهای آینده فقط *پیش‌بینی* می‌شوند و چیزی ذخیره نمی‌شود تا وقتی کاربر واقعاً کاری با آن‌ها بکند.

### هدف‌ها

هدف هر روز از `Settings` می‌آید: `weekdayGoalMinutes[روزِ هفته]` و اگر `null` باشد، `dailyGoalMinutes`. عدد `0` یعنی آن روز اصلاً نمره‌گذاری نمی‌شود — نه موفق حساب می‌شود و نه زنجیره را می‌شکند. `successThreshold` سهمی از هدفِ همان روز است که «روز موفق» را می‌سازد؛ مثلاً شنبه با هدف ۶ ساعت و قانون ۷۰٪ یعنی ۴ ساعت و ۱۲ دقیقه.

### مهاجرت از نسخه‌ی پیشین

نسخه‌ی ۱ فقط می‌دانست چه چیزی تیک خورده، نه چقدر طول کشیده. پس رکوردهای قدیمی با **صفر دقیقه** بازیابی می‌شوند تا زمانی از خودمان درنیاوریم؛ سابقه‌ی *برنامه* دست‌نخورده می‌ماند و ساعت‌ها از همین‌جا شروع به جمع شدن می‌کنند. `dailyGoal` قدیمی (سهمی از فهرست روز) به `successThreshold` تبدیل می‌شود، چون همان عدد پاسخ صادقانه‌ی «چه سهمی از ساعت‌های امروز» هم هست.

### ذخیره‌سازی

فعلاً همه‌چیز محلی است (`localStorage`)، پشت یک `DataRepository`. هیچ حساب کاربری، هیچ سرور، هیچ هزینه‌ای. برای افزودن همگام‌سازی در آینده کافی است یک آداپتور تازه پیاده شود؛ رابط کاربری تغییری نمی‌کند.

### طراحی

راهنمای طراحی پروژه در `.claude/skills/frontend-design/` است و جهت‌گیری بصری از آن می‌آید:

- **زمینه** صفحه‌ی یک نسخه‌ی خطی است، نه داشبورد: کاغذ نخودی با سطرکشی بسیار کم‌رنگ، و مرکّبی که لاجوردی‌ـ‌سیاه است نه سیاه خنثی.
- **دو رنگ، دو کار**: فیروزه‌ی نیشابوری همه‌ی کنش‌ها را می‌برد، و طلای تذهیب فقط خرج چیزی می‌شود که ارزش جشن دارد — روزی که به ساعتش رسیده، یا زنجیره‌ای که زنده است.
- **دو قلم، دو نقش**: «لاله‌زار» از حروف‌نگاری پوستر و تابلوی ایرانی می‌آید و فقط سه جا ظاهر می‌شود (نام برند، عنوان صفحه، ساعت روی شمسه)؛ «وزیرمتن» بقیه‌ی کار را می‌کند، چون خوانایی رابط فارسی جایی برای تفنن نیست.
- **قرص ساعت**: هیروِ «امروز» یک حلقه است، تقسیم‌شده به تعداد ساعت‌های هدف آن روز — شش دندانه یعنی شش ساعت، بدون خواندن عدد. ساعت‌های بیشتر از هدف، قوس نازک فیروزه‌ای بیرونِ حلقه‌اند: قرص بزرگ می‌شود، نه اینکه روی خودش برگردد.
- **هفته زیرش**: هفت شمسه‌ی کوچک، نه یک حلقه‌ی دوم. شکلِ هفته سریع‌تر از عددی خوانده می‌شود که بیشترش دوباره همان امروز است.
- **امضای بصری**: *شمسه*. هفته یک برگ در روز رشد می‌کند — شنبه یک برگ، جمعه هفت — پس شکلِ هر روز خودش می‌گوید کدام روز است و هفته یک توالی خوانده می‌شود، نه هفت نشانِ متفاوت. برگ‌ها با جمع شدن ساعت‌ها روشن می‌شوند و فقط روزی که به آستانه‌ی موفقیت رسیده طلایی می‌شود. حلقه‌ی «امروز» هم به‌جای درصد، به تعداد ساعت‌های هدف آن روز دندانه دارد.

### وابستگی‌ها

فقط Next.js، React و Tailwind. تقویم جلالی، نمودارها، آیکون‌ها، انیمیشن‌ها و اجزای رابط کاربری همگی داخل پروژه نوشته شده‌اند — سبک‌تر، قابل کنترل‌تر در RTL، و بدون ریسک وابستگی.
